## Задача и формат

За 90 минут ваша группа исследует незнакомый публичный API, пишет к нему Python-клиент на `requests` и защищает решение.

### Легенда
Ваша команда подключает офисную кофемашину к внешнему каталогу напитков. У поставщика есть публичный HTTP API — [SampleAPIs Coffee](https://pycourse-2026.duckdns.org/coffee/hot/). Готовой спецификации нет: перед интеграцией нужно самостоятельно выяснить, как API себя ведёт, и написать клиент, который умеет получать список горячих напитков, находить напиток по `id`, создавать, изменять и удалять запись.
### Результат
Один запускаемый Python-файл (на основе `starter.py`) с описанием запроса создания кофе и защита решения.

## Этап 1. Исследование API

До написания кода группа должна сама выяснить, как устроен API. Структура данных напитка не выдаётся — её нужно определить запросами.

Определите:

- адреса коллекции и отдельного ресурса;
- какие HTTP-методы доступны;
- форму успешных ответов;
- фактические коды статуса для каждой операции;
- что возвращается при запросе отсутствующего ресурса;
- какие данные нужны, чтобы создать горячий кофе.

Инструменты — любые: браузер, `curl` или небольшой Python-скрипт. Начинайте с безопасных GET-запросов.

**Правила работы с общим API.** API публичный, им одновременно пользуются все группы и другие люди.

- Изменяйте и удаляйте только записи, которые создала ваша группа.
- Добавляйте в название своей записи уникальную метку группы.
- Не удаляйте и не меняйте чужие записи, даже ради эксперимента.

Вы получаете один файл `starter.py` с зависимостями, базовым URL, исключениями, интерфейсом клиента и каркасом сценария. Работайте в этом одном файле; `requests.Session()` не используйте.

    created_id = None
    try:
        # GET коллекции.

        # Сразу сохраните id из ответа в created_id.
        # GET: сравните сохранённые поля с отправленными.
        # PUT и повторный GET: проверьте все заменённые поля.

        # и убедитесь, что остальные поля сохранились.

Как читать интерфейс:

- имена методов показывают, какие операции нужны;
- `base_url` и `timeout` — общие настройки клиента, их не нужно повторять в каждом методе;

- `_request()` — место для общей HTTP-логики;
- `replace_drink()` выполняет PUT и заменяет напиток целиком, `update_drink()` выполняет PATCH и меняет только переданные поля;
- поля напитка, тела запросов, статусы и правила проверки вы определяете сами.

## Этап 2. Реализация клиента

Реализуйте методы выданного интерфейса и соберите в `main()` единый сценарий из восьми шагов.

1. Получить список горячих напитков.
2. Создать новый напиток с уникальной меткой группы в названии.
3. Получить созданный напиток по `id`, который вернул сервер.
4. Полностью заменить данные напитка через PUT.
5. Изменить часть данных через PATCH.
6. Повторно получить напиток и проверить изменения.
7. Удалить созданный напиток.
8. Повторить GET по этому `id` и корректно обработать отсутствие ресурса.

**Работа с созданной записью.** Используйте только `id` из ответа на ваш POST. Даже если сценарий упал в середине, программа должна попытаться удалить запись, если её `id` известен. Если POST завершился тайм-аутом, результат создания неизвестен: сообщите об этом и выведите метку для ручной проверки. Автоматически повторять POST нельзя.

### Требования к программе

- Запросы выполняются через библиотеку `requests`.
- Тайм-аут задаётся для каждого запроса.
- HTTP-статус проверяется до использования тела ответа.
- Проверяется, что `Content-Type` — JSON; для ответа без JSON-тела `.json()` не вызывается.
- Отсутствие ресурса (`404`) отличается от остальных ошибок API.
- В ожидаемых сценариях программа не падает с необработанным исключением.
- Используется `id`, возвращённый POST-запросом.
- Созданная запись удаляется в конце.
- В консоль выводятся понятные этапы сценария.

Обязательная часть — HTTP-клиент, сравнение сохранённых данных с отправленными и обработка ошибок. Дополнительно, если останется время: локальная проверка значений (непустые строки, состав `ingredients`, неизвестные поля).

**Повторы (retry) не реализуются**, в том числе для GET. О правилах повторов поговорим на защите: подумайте, какие запросы можно безопасно повторить, а какие нет.
